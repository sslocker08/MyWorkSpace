# 成果物レビュー関門・レビュータブ 要件定義（正本）

2026-06-12 採用（dec-007）。規程＝本書 §1-2、実装要件＝§3-6（実装担当：EC・情報システム部＝req-hq-007）。

## 1. 目的
- 社長が各部署の成果物を**視覚的に**レビューしてからタスクをクローズする関門を設ける。
- 成果物の要約はローカルLLM（Ollama）に任せ、Claudeトークンを消費しない。
- 既存の単一書き手原則・fbk下り線・build生成の仕組みに乗せる（新しい書き込み面は作らない）。

## 2. 運用規程（タスククローズの関門）
- **レビュー必須**：次のいずれかに該当するタスクは、社長レビュー（承認）を経ずに「完了」にしてはならない。
  1. 難易度「大・特大・超特大」のタスク
  2. 対外に出る成果物（公開コピー・プレス・提案資料・本番反映）
  3. 部長が「社長レビュー要」と判断したもの／HQがfbkで指定したもの
- **例外（自動クローズ可）**：小・中タスクで影響が自部署内に閉じるもの＝従来どおり部長判断で完了化。
- **フロー**：
  1. 部署：タスク完了の前に、自部署ステータスの「成果物（レビュー用）」表に行を追加（ステータス=レビュー待ち）→ build
  2. 社長：ダッシュボード「レビュー」タブ（操作モード＝serve.js）で内容確認 → カードの**承認/差戻しボタン**を押す → 一言（任意）を入力 → **Ollama が部署向けの通知文を生成** → `fbk-hq-NNN`（対象=タスクID・判定=承認/差戻し・内容=生成文）が HQ.md に自動記録 → build 再生成 → 画面が即更新
  3. 部署：自分宛fbkを確認し、承認→成果物行を「承認済」にしてタスクを完了化／差戻し→修正して状態を「レビュー待ち」に戻す（再提出）
- **派生ステータス（単一書き手の維持）**：serve.js が書くのは HQ.md の fbk だけ。成果物の「承認済/差戻し」表示は build.js が**最新の fbk 判定から派生**して即反映する（社長が押した瞬間にダッシュボードへ反映され、部署の行確定を待たない）。部署は次回起動で自分の成果物行を同期する。
- **レビュー要否タグ（タスク表）**：build.js が各タスクに `関門` タグを機械付与する。判定＝**優先度=最高／モデル∈{Opus,Fable,Ultracode}／そのタスクに社長レビュー成果物がある**のいずれか。タグ付きタスクは承認まで完了化しない。これは下限の自動判定で、該当しなくても部長・HQが「レビュー=社長」の成果物を出せば関門化できる。
- **機械検証**：build.js は「レビュー=社長 かつ 派生ステータス≠承認済」の行のタスクIDがタスク表で「完了/中止」になっていたら**警告を出す**（関門すり抜けの検知）。

## 3. データモデル（status-template.md に追加済みの新セクション）
```
## 成果物（レビュー用）
| タスクID | 成果物（パス） | 種別 | レビュー | ステータス | 提出日 |
```
- 種別：`文書 / 画像 / コード / 集計 / その他`
- レビュー：`社長 / 部内 / 自動`（関門対象は「社長」のみ。部内/自動は記録用）
- ステータス：`レビュー待ち / 承認済 / 差戻し / 取下`（列名は語彙規程どおり「ステータス」）
- 1成果物1行。パスはKIBIルートからの相対パス。複数成果物は複数行（同じタスクIDでよい）。

## 4. UI要件（ダッシュボード）
- タブ順：**概況｜レビュー｜タスク｜連携｜判断｜履歴｜モデル**（レビューは概況の次。バッジ=レビュー待ち件数）。
- レビュータブ内に**部署別の小タブ**（9部署・各バッジ=レビュー待ち件数。0件の部署はグレー表示）。
- 成果物ごとの**カード表示**：
  - ヘッダ：タスクID（クリックでタスクタブの該当行へ）・タスク名（タスク表から突合）・部署・提出日・状態チップ
  - 本文：レビュイー要約の**結論**（§7。未生成は「自動生成中…」＋原文ティーザー）＋成果物パス＋要約状態フラグ（要約/要再生成/自動生成中/—）
  - フッタ：`承認`・`差戻し` ボタン（操作モード serve.js のみ稼働。押下→Ollama生成→`/review`→fbk記録→build→reload。閲覧モード file:// では起動手順を案内）
  - **カードクリックで全画面2ペインモーダル**（§7）。左＝レビュイーコメント／右＝原文。その場で承認/差戻し・要約生成ができる。
- 状態フィルタ（既定=レビュー待ちのみ表示。承認済・差戻しも切替で閲覧可）。
- 1画面タブ式・既存の和紙×墨デザイン・共通フィルタの作法を踏襲。`boards/review.md` も併せて生成（テキスト面）。

## 5. Ollama生成の基本要件（→ 詳細は §7）
- ローカル Ollama API（http://localhost:11434）。既定モデル `qwen2.5:14b`（環境変数 `OLLAMA_MODEL`）。`num_ctx` は 8192 で成果物本文が文脈に収まるようにする。
- キャッシュ：`Internal/Secretary/dashboard/summaries/<タスクID>__<ファイル名>.md`。先頭に `<!-- sha:<成果物SHA> ctxsha:<文脈SHA> ... -->`。成果物 or タスク文脈が変わると再生成。
- **遮断**：`_Records/` 配下・個人情報を含むパスは対象外（集計値の成果物を出す）。
- **Ollama不在・失敗時**：build/serve は Ollama 無しでも全機能動作。資料がなければカード=冒頭抜粋、モーダル=本文抜粋＋「未生成」表示。
- build.js 本体は Ollama を呼ばない（決定的・高速。キャッシュの埋め込みのみ）。生成は `review-summarize.js`（バッチ）と `serve.js /gen-review`（1件オンデマンド）が `review-core.js` 経由で行う。

## 7. レビュイーAIとレビュー資料・詳細モーダル（2026-06-12 dec-009）
冒頭の生markdown抜粋では中身が分からない、という課題への対応。

- **ペルソナ**：Ollamaは**レビュイー（実施部署の代弁者）**として振る舞う。自分が担当として責任を持って成果物を説明・弁護し、レビュアー（社長）が承認/差戻しを判断するのに必要な情報を先回りして**正直に**示す。誇張・粉飾しない。未確認は「未確認」と書く。簡潔体。
- **入力コンテキスト**（`review-core.js` が組み立て）：①タスク行（名称・ステータス・トリガー・関係部署・担当・モデル・進捗・優先度＝`boards/tasks.md`）②**前後関係**＝そのタスク/部署が絡む部署間依頼の往復（`boards/requests.md` から最大10件）③成果物本文（テキスト・上限50KB）。
- **出力（markdown・固定見出し）**：`## 結論` / `## このタスクの位置づけ・前後関係` / `## やったこと` / `## 主要な判断と根拠` / `## 留意点・残課題・リスク` / `## レビュアーへのお願い`。
- **原文は置き換えない**：要約は**結論に集約**し、原文（成果物本文）は常に並べて表示する。カード面＝結論（`## 結論` を1〜2行・markdown記号を外す）。原文が無いと判断材料が消えるため、要約で原文を上書きしない。
- **対象は中身がテキストの成果物すべて**：拡張子でなく内容（先頭4KBにNULバイトが無いか）で判定。**コード・設定ファイルも要約対象**で、結論＝「何をするためのコードか（目的）」、やったこと＝主な動作・構成・連携、として説明する。50KB超は先頭から切り詰めて投入（全文はパス参照）。
- **対象外でも必ず情報を出す（レビュイーコメント空白の禁止）**：①パス未記入②保護領域(_Records 等)③ファイル不在④非テキスト(画像/PDF 等)＝いずれもレビュイーコメント欄に「理由＋どうレビューすべきか」を、原文欄に「メタ情報（ファイル名・形式・サイズ・更新）または状況」を表示する。保護領域は内容を読まずに案内のみ（防火壁）。
- **自動生成（トリガー不要）**：レビューに回った成果物（`.md/.txt` の未生成分）は、`serve.js` がページ配信のたびに**背景で自動生成**する（`autoGen`＝未生成があれば `review-summarize.js` を非ブロッキングで起動。多重起動はフラグで防止）。カードは「要約 自動生成中…」を表示し、生成済みから順に結論が出る。モーダルを閉じている間だけ約25秒ごとに自動リロードして反映。手動の即時生成はモーダルの「生成」ボタン＝`serve.js /gen-review`→`review-core.genReviewDoc`。全件バッチ＝`node Internal/Secretary/tools/review-summarize.js [taskId [path]]`（`FORCE=1`で再生成）。
- **キャッシュ無効化は成果物本文の変更時のみ**（先頭 `<!-- sha:<成果物SHA> -->`）。依頼ボードの更新では再生成しない（ctxshaは記録のみ）。
- **詳細モーダル（全画面・2ペイン）**：カードクリックで開く。**左＝レビュイーコメント**（Ollamaの固定見出し資料をmarkdown整形表示）／**右＝原文**（成果物本文をmarkdown整形表示・パス明示）。狭い画面では縦に積む。フッタに成果物パス＋`承認`/`差戻し`＋（未生成/要再生成なら）`生成`ボタン。承認/差戻しは §2 の `/review` 経路（Ollamaが部署向け通知文を生成→fbk→build→画面即更新）。Escape/背景クリックで閉じる。
- **単一書き手の維持**：生成は `summaries/` キャッシュにのみ書く（部署ファイル不変）。承認/差戻しは HQ.md の fbk のみ。成果物の承認済/差戻しは fbk から派生表示（§2）。
- **受け入れ条件**：①カードに結論が出て、クリックで全画面2ペイン（左コメント／右原文）が開く ②レビュー入りの成果物が背景で自動生成され、リロードで順次反映される ③モーダルから即時生成・承認・差戻しでき画面が更新される ④Ollama不在でも原文表示にフォールバック ⑤`_Records/`遮断 ⑥生成JSの構文自己チェック通過。

## 6. 実装分担・段階導入・受け入れ条件
- **分担**：規程・様式＝社長室（本書・status-template・operations.md）。実装＝**社長指示により社長室が直接実装（2026-06-12 P1・P2完了、req-hq-007は取下）**。以後の保守＝EC・情報システム部。
- **P0（即日・実装不要）**：各部署が「成果物（レビュー用）」表を書き始める。社長レビューはパス直読みで暫定運用。
- **P1**：boards/review.md＋レビュータブ（小タブ・カード・抜粋表示・承認/差戻しボタン・関門警告）。
- **P2**：Ollamaサマリー（review-summarize.js＋キャッシュ）。
- **受け入れ条件**：①レビュー待ち成果物が部署別に視覚表示される ②承認クリック→fbk-hq記録→部署クローズの一巡が回る ③関門対象タスクの先行クローズをbuildが警告する ④Ollama無しでも全機能動作 ⑤_Records/遮断が効いている ⑥生成JSの構文自己チェック通過。

## 8. 判定の記録・社長コメント・対応方針・再提出ループ（2026-06-12 dec-010）
承認/差戻し後の処理が確実に回ることを保証する。

- **判定記録**：`/review` で承認/差戻しすると、serve.js が `dashboard/summaries/_verdicts.json` に記録する（`taskId → {verdict, date, fbkId, presidentNote(原文), deptMessage, responsePlan, files{パス:SHA}}`）。fbk(HQ.md)は人間可読の正本、_verdicts.json は再提出検知と社長コメント保管の操作用ファイル（単一書き手：部署ファイルには書かない）。
- **社長コメント原文の保存**：社長が入力したコメントは加工前の原文を `presidentNote` に保存。カードに「💬 社長: …」を表示し、モーダルの判定バナーに全文を表示する（Ollama整形後の部署通知文 deptMessage とは別に原文を残す）。
- **対応方針（レビュイー応答）**：社長コメントがあるとき、Ollamaが**担当部署（レビュイー）として「コメントを受けてどう対応するか」**を背景生成し（`review-core.genReviewDoc` ならぬ `genResponsePlan`）、判定バナーに表示。承認＝指摘反映→完了化の段取り、差戻し＝修正方針→再提出の段取り。クリックは待たせない（背景生成→次のリロードで反映）。
- **再提出ループ（自動）**：判定時に成果物の SHA を記録。**成果物が判定後に更新されると、build.js が実効ステータスを自動で「レビュー待ち」へ戻す**（＝差戻し→部署が直す→自動で再レビューに回る）。部署のステータス手戻し操作は不要。承認後に更新された場合も再レビュー待ちへ戻る（不用意な事後改変の検知）。
- **承認済バッジ**：承認済/取下はカード右下に固定バッジ（緑＝承認済／黒＝取下）。フッタは下端ぞろえ。
- **受け入れ条件**：①承認/差戻しで `_verdicts.json` に記録される ②社長コメント原文がカード/モーダルに残る ③対応方針が背景生成されモーダルに出る ④成果物を直すと自動で「レビュー待ち」へ戻り再レビューできる ⑤承認済バッジが右下固定。（全項目を 2026-06-12 実機検証済み）
