# 全社運用規程 ── 部署間連携・朝礼夕礼・進捗可視化

正本。2026-06-11 採用（dec-002・dec-003、社外監査役提案に基づく）。2026-06-12 三社体制移行で旧 `Shared/` は `Internal/Secretary/` へ（規程は連続）。
目的：チャットルームに分かれた会社を1つのチームとして機能させる。会話ではなく**状態**を管理する。
パス表記：本書を含む規程・ボード・成果物表のパスは**KIBIルート相対**（例 `Internal/Secretary/status/HQ.md`）。席で実行するコマンドは席相対（社長室＝`Secretary/...`、部署＝`../Secretary/...`）。

## 1. 設計原則

1. **単一書き手原則**：1ファイル1書き手。各部署が書くのは自部署の `Internal/Secretary/status/<自部署>.md` だけ。
   部署セッションは並行して動くため、共有ファイルへの同時書き込みは構造的に排除する。
2. **正本一元化（SSOT）**：1つの事実は1箇所にだけ書く。ほかはパスと ID で参照する。
3. **ボードは生成物**：全社ボードとダッシュボードは `tools/build.js` が status/ から機械生成する（トークン消費ゼロ）。手編集禁止。

## 2. ファイル構成と書き手

| ファイル | 役割 | 書き手 |
|---|---|---|
| `status/<部署>.md` ×10 | 部署の全状態（タスク・依頼・詰まり・判断依頼・アピール） | その部署のみ |
| `boards/tasks.md` | 全社タスク一覧 | 生成 |
| `boards/requests.md` | 部署間依頼ボード（依頼元と宛先の行を ID で突合） | 生成 |
| `boards/blockers.md` | 詰まり・障害ボード | 生成 |
| `boards/judgments.md` | 社長室判断待ち一覧 | 生成 |
| `boards/feedback.md` | 社長フィードバック一覧（正本は `status/HQ.md`） | 生成 |
| `boards/bulletin.md` | 全社掲示板（各部署のアピール・共有の集約） | 生成 |
| `boards/decisions.md` | 意思決定ログ | 社長室のみ |
| `daily/YYYY-MM-DD.md` | 日報（朝礼統合＋夕礼統合） | 社長室のみ |
| `dashboard/index.html` | ダッシュボード | 生成 |

## 3. ID 規約

`種別-部署コード-連番`。採番は発生元の部署が行う（自分のファイル内で完結するため衝突しない）。

- `tsk-mkt-001` … タスク（MKT発）
- `req-fin-001` … 部署間依頼（**依頼元**が採番。宛先は同じIDで自分の対応表に書く）
- `blk-web-001` … 詰まり・障害
- `jdg-web-001` … 社長室への判断依頼
- `fbk-hq-001` … 社長フィードバック（社長室のみ）
- `dec-001` … 意思決定（社長室のみ・部署コードなし）

IDはすべて**小文字**で書く。

部署コード：HQ（社長室）/ PLN（経営企画室）/ BRD（ブランド戦略室）/ PRD（製品開発部）/
WEB（EC・情報システム部）/ MKT（マーケティング部）/ MED（広報部）/ SLS（営業部）/
FIN（経理・財務部）/ LGL（法務・コンプラ部）。

## 4. 語彙の統一（表記ゆれ禁止）

- 列名は「ステータス」（「状態」とは書かない）。判断依頼の件名列は「内容」。
- タスクのステータス：`未着手 / 進行中 / レビュー待ち / 他部署待ち / 社長室判断待ち / 保留 / 完了 / 中止`
- 優先度：`最高 / 高 / 中 / 低`
- 依頼状態（依頼元視点）：`依頼中 / 完了 / 取下`
- 依頼状態（宛先視点）：`受領 / 対応中 / 回答済 / 保留`
- 詰まり状態：`未対応 / 対応中 / 他部署待ち / 社長室判断待ち / 解消 / 保留`
- 緊急度：`高 / 中 / 低`
- アピール種別：`共有 / 依頼 / 注意 / 完了報告 / 成果物公開 / 相談`
- タスク表の「担当者」は「担当」を省いた役名（例: 香調企画）、「モデル」は実際に使うClaudeモデルを書く。
- タスク表の「トリガー」：ステータスが待ち系のとき、堰き止めている `req-`／`jdg-` のIDを書く（ダッシュボードでリンクになる）。
- **タスク名は全角20字目安で簡潔に**。詳細は成果物や依頼の内容欄へ。ダッシュボードは横スクロールさせない。
- タスクを「完了/中止」にしたら**「完了日」**（YYYY-MM-DD）を記入する。履歴タブは完了日で表示する。
- **クローズ関門**：大・特大・超特大、対外に出る成果物、部長/HQ指定のタスクは、「成果物（レビュー用）」表で社長承認（fbk）を得るまで「完了」にしない。小・中で自部署内に閉じるものは部長判断で完了化可。正本＝`rules/review-gate.md`。

## 5. 部署間依頼の流れ（ID 連結）

1. 依頼元：自分のステータス「他部署への依頼」表に行を追加（ID・宛先・内容・緊急度・期限・状態=依頼中）。
2. 生成：`node Internal/Secretary/tools/build.js` → `boards/requests.md` に載る。
3. 宛先：requests.md（または自分宛の行）を見て、自分のステータス「受けた依頼への対応」表に同 ID で行を追加（受領→対応中→回答済。回答は成果物のパスで）。
4. 依頼元：回答を確認したら自分の行を 状態=完了 にする。
5. 双方完了の行は週次アーカイブで `archive/` へ。
6. **受領SLA**：自分宛の依頼（requests.md で宛先=自部署・未受領のもの）は、**次回セッション開始時に必ず受領記録を書く**（受領→対応中/回答済/保留のいずれかへ）。放置検知はダッシュボードの「未受領」表示で行う。

## 5b. 社長フィードバック（双方向の下り線）

部署→社長室の上り線（jdg・夕礼・アピール）に対する、社長室→部署の下り線。

1. 社長室が `status/HQ.md` の「部署へのフィードバック」表に行を追加（`fbk-hq-連番`・宛先・対象ID・判定・内容）。
   判定：`承認 / 差戻し / コメント / 保留`。
   記入経路は2つ：**①社長室チャットで指示**（議論が要る案件）／**②ダッシュボード上の操作**（`node Internal/Secretary/tools/serve.js` 起動中のみ。判断待ち行の承認・差戻しボタンとフォームから直接記入できる。即決向き）。
2. 生成：build で `boards/feedback.md` とダッシュボードに反映。
3. 宛先部署：セッション開始時に自分宛のフィードバックを読み、**対象タスク・判断の状態を更新することで応える**（承認→着手、差戻し→修正して再提出。これが返信）。
4. その状態変化がまたダッシュボードに上がり、輪が閉じる。フィードバック行自体は履歴として残す。

## 6. 朝礼・夕礼

- **朝礼**：各部署が自部署ステータスの「今日やること（朝礼）」とタスク表を更新 → 社長室が build 実行 →
  status/ を読んで `daily/YYYY-MM-DD.md` の「朝礼統合（本日の全社方針）」を作成。
- **夕礼**：各部署が「今日の結果（夕礼）」とタスク表を更新 → 社長室が build 実行 → 同ファイルに「夕礼統合（本日の全社まとめ）」を追記。
- 様式：`templates/daily-template.md`。部署別は各1行。詳細はステータスファイルが正本。
- 翌朝、朝礼欄・夕礼欄は書き換える（前日分は daily/ に統合済み）。

## 7. 日中の随時更新（トリガー8つ）

次のとき自部署ステータスを更新し、build を実行する：
①新タスク発生 ②タスク状態の変化 ③他部署への依頼発生 ④詰まり発生
⑤社長室判断が必要になった ⑥重要成果物の完成 ⑦重要な意思決定 ⑧期限・優先度の変更。

## 8. 週次アーカイブ（社長室・金曜夕礼後）

- 各ステータスの「完了/中止」タスク行・双方完了の依頼行・「解消」詰まり行・対応済みフィードバック行を `archive/YYYY-Www.md` へ**移動**する（削除ではない。**タスクは会社の履歴として永続保存**し、ダッシュボードの「履歴」タブが archive/ も含めて表示する）。
  ※アーカイブ作業のみ、社長室が各部署ファイルの完了済み行を移動してよい（唯一の例外。内容の編集は不可）。
- 前週の daily/ を `archive/daily/` へ移す。
- 目的：ステータスファイルを常に「現役の行だけ」に保ち、全セッションの読み込みトークンを抑える。履歴は archive/ に全量残る。

## 9. ダッシュボード

- `node Internal/Secretary/tools/build.js` が `dashboard/index.html` を生成。ブラウザで直接開ける（閲覧はサーバ不要）。
- **1画面・タブ式**（ページスクロールなし）：①概況（左→右の指揮系統フロー＋連携クラスタ＋本日の全社方針）②**レビュー**（成果物レビュー関門＝部署小タブ×状態フィルタ×カード。正本 `rules/review-gate.md`）③タスク（現役一覧・部署順→ID順）
  ④連携（**現役のみ**＝依頼中の依頼・未解消の詰まり・掲示板）⑤判断（判断待ち・社長フィードバック・意思決定ログ）⑥履歴（完了タスク＝**完了日**表示＋**完了した依頼・解消した詰まり＝連携タブから移管**＋archive/全量）⑦モデル（ブレットグラフ・規程目安との比較）。
- ID（トリガー部署列・回答参照欄など）をクリックすると該当タブの該当行へ飛び、3秒間に5回点滅する。
- タスク・連携・判断・履歴の各タブに**共通フィルタ**（部署／ステータス／モデル／進捗［未着手・仕掛中・完了］／優先度＋検索。同時適用＝AND、リセットボタンあり）。
- **操作モード**：`node Internal/Secretary/tools/serve.js` で http://localhost:4310 を開くと、判断タブ・**レビュータブ**から
  社長フィードバックを直接記入できる（HQ.md に追記→自動再生成。書くのは社長のみ＝単一書き手原則は維持）。
  レビュータブの承認/差戻しは Ollama が部署向け文面を生成して fbk 化し、成果物の承認済/差戻しは fbk から派生表示される（正本 `rules/review-gate.md`）。
- 色分け：緑=順調／黄=注意（期限接近・他部署待ち）／赤=詰まり／青=レビュー待ち／紫=社長室判断待ち／灰=保留／黒=中止。

## 10. ワンチーム十箇条

①状況を隠さない ②詰まりは早めに共有 ③依頼は明確に（ID・期限・緊急度）④成果はアピール欄へ
⑤他部署の成果を参照する ⑥依存関係を明示する ⑦判断待ちを放置しない ⑧進捗率より「次の行動」
⑨完了・未完了・保留を曖昧にしない ⑩全社最適を優先する。

## 付記：監査役原案からの正規化（dec-003）

| 原案の様式 | 本実装での扱い |
|---|---|
| 部署別ステータスファイル | `status/<部署>.md`（唯一の書き込み面に昇格） |
| 全社タスク管理表 | `boards/tasks.md` に**生成**（正本は各ステータスのタスク表） |
| 部署間依頼ボード | `boards/requests.md` に**生成**（正本は依頼元＋宛先の両ステータス） |
| 詰まり・障害ボード | `boards/blockers.md` に**生成** |
| 全社掲示板 | `boards/bulletin.md` に**生成**（正本は各ステータスのアピール欄） |
| 今日の成果・アピールボード | 夕礼欄＋アピール欄に統合（掲示板生成に含む） |
| 意思決定ログ | `boards/decisions.md`（社長室の直接記入。原案どおり） |
| 朝礼・夕礼の個別報告書 | ステータスの朝礼欄・夕礼欄に統合（ファイル乱立を防ぐ） |
| 全社方針・全社まとめ | `daily/YYYY-MM-DD.md` に統合（1日1ファイル） |

理由：同じ事実の多重記入（最大3箇所）を排除し、二重報告・古い情報・同時書き込み衝突・トークン浪費を構造的に防ぐ。
