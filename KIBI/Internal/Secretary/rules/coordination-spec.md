# ダッシュボード再構成・社内便（スレッド連携）要件定義 ── 正本

2026-06-12 起案（dec-012 予定）。ダッシュボードのタブ統一と、部署間のリアルタイム連携（社内便）の設計。
実装はフェーズ分割（§8）。レビュー関門・単一書き手・build競合回避の既存原則を一切崩さない。

## 1. 原則（非交渉）
- **単一書き手**：書けるのは自部署ステータス（と自部署フォルダ）だけ。**受信箱は受信側が持たない**＝送信者所有。
- **派生ビュー**：受信箱・スレッド・マトリクスはすべて build.js が生成する**ビュー**。物理90ファイルは作らない（内部的にも干渉ゼロ）。
- **build は Ollama非依存・決定的**。生成系（要約・論点整理・対応方針）は review-core 経由で serve.js / バッチが行いキャッシュ。
- カード／モーダル／状態フィルタ／自動更新の作法は**全タブ統一**。

## 2. タブ構成（並び・改称）
順：**組織図｜タスク｜ジャッジ｜レビュー｜連携｜履歴｜モデル**
| id | 表示 | 旧 |
|---|---|---|
| home | 組織図 | 概況 |
| tasks | タスク | - |
| judge | ジャッジ | 判断 |
| review | レビュー | - |
| links | 連携 | - |
| history | 履歴 | - |
| model | モデル | - |
- 「フィードバック履歴」「意思決定ログ」は judge から **履歴タブへ移管**。

## 3. ジャッジタブ ＝ レビュータブと完全同一化（フロント／バック）
- データ源＝各ステータスの「社長室への判断依頼」(jdg)。レビュー（成果物）と jdg を「レビュー可能アイテム」として同一UIで扱う。
- カード：jdg-ID・部署・論点・期限・状態（派生）。カード面に**結論＝起票部署の推奨**。
- クリック→全画面2ペイン：左＝**論点整理＋推奨**（Ollama が起票部署＝レビュイーの代弁として、選択肢・トレードオフ・推奨を生成。`review-core.genJudgeBrief`）／右＝**参照資料の原文**（jdg 背景中のパスを検出して表示、無ければ背景テキスト）。
- 承認／差戻し＝`/review` と同一経路（対象=jdg-ID）。承認＝判断採用、差戻し＝再検討。社長コメント原文保存・対応方針生成・判定記録・自動再提出ループも同一。
- バック：`build.js` のカード/モーダル生成を jdg にも適用。`serve.js` は jdg 対象の判定も処理（既存 /review で対応可）。

## 4. 社内便（スレッド型・送信者所有）＝ 連携タブの土台
### 4.1 データモデル（status-template に新セクション）
```
## 社内便（送信）
| 便ID | スレッド | 宛先 | 種別 | 件名 | 本文/パス | 状態 | 日時 |
```
- `便ID`＝`bin-<自コード>-NNN`（自部署採番・1メッセージ1行）。
- `スレッド`＝会話の束ねID。新規は自分の便IDを用い、**返信は元スレッドIDを引き継ぐ**。タスク/依頼に紐づくなら `tsk-…`/`req-…` を流用してよい。
- `宛先`＝相手部署（社長室含む）。
- `種別`＝`連絡 / 申し送り / 相談 / 返信 / 完了`。
- `件名`＝一覧用の短い主題。`本文/パス`＝markdown短文 or 成果物パス。
- `状態`（送信者視点）＝`送信 / 対応中 / 完了`。
- `日時`＝`YYYY-MM-DD HH:MM`（JST）。
- **各部署は自分の送信行だけ書く**（差出人＝自部署）。**返信も自分の送信行**として、同じ `スレッド` を付けて書く。

### 4.2 派生ビュー（build.js が生成）
- **スレッド**＝全部署の社内便を `スレッド` で束ね、`日時` 昇順に並べた会話。
- **受信箱（インボックス）**＝各部署について「自分が宛先のスレッド」の集合。**要対応**＝最新メッセージが自分宛で、自分の返信がそれより新しくないもの。
- `boards/mail.md`（テキスト面）と、後述の連携タブ（視覚面）に出力。

### 4.3 返信・スレッド継続・クローズ
- **タスク/依頼がクローズするまでやり取りを継続**。スレッドは関連タスク/依頼の状態に追従し、`種別=完了` か関連タスク完了で閉じる。
- ダッシュボードからの返信＝**社長（HQ）のみ**。serve.js が HQ.md の社内便（送信）に1行追記（差出人=社長室・同スレッド・種別=返信）。他部署の返信は各自のセッションで自部署ステータスに書く（単一書き手）。

## 5. 連携タブ ＝ カード化（社内便インボックス＋既存依頼/詰まりの統合）
- **スレッドカード**：1スレッド＝1カード。主題（件名）・参加部署・最新メッセージ抜粋・状態・**「要対応」フラグ**（自分＝社長宛で未返信のもの強調）。
- 既存の `req`（型あり・状態追跡）・`blk`（詰まり）も**カード化**して同居（種別タグで区別）。req は依頼元→宛先・状態 元→先。
- クリック→モーダル：スレッドの**会話全文**（差出人ごとのバブル：部署・本文・日時）＋（操作モードなら）**返信ボックス**（社長が返信を1行追記）。req は往復＋回答。
- フィルタ・挙動は全タブ統一。掲示板(bulletin)はカード下に従来表示。

## 6. 複数部署タスクのブレークダウン（運用ルール）
- 複数部署が絡むタスクは、起票部署（または社長室）が**サブ依頼/社内便に分解**し、`スレッド` で束ねる。
- **順番に段階を追う**＝前段の宛先が `回答済/完了` になってから次段を起票。**並行可能なら並行**で複数宛先に同時起票。
- 各段の成果物は通常どおりレビュー関門へ。スレッドは全段が閉じるまで継続。
- `/Chack` がこの分解・段階処理を担う（自部署フォルダに成果物、ステータス更新と build は席が最後に一度だけ）。

## 7. リアルタイム化（60秒自動更新）
- クライアントが**60秒ごとに自動リロード**。ただし**モーダルを開いている間・入力中・返信中は停止**（既存の pending 自動リロードと同じ作法を一般化）。
- serve.js は GET毎に build 済＝near-real-time。生成系（Ollama）は背景・キャッシュで非ブロッキング。

## 8. 実装フェーズ・受け入れ条件
- **P1（小・即）**：タブ並び・改称（組織図/ジャッジ）＋履歴へFB履歴・意思決定ログ移管＋60秒自動更新。
- **P2（中）**：ジャッジ＝レビュー同一化（jdgカード・2ペイン・論点整理生成・承認/差戻し）。
- **P3（大）**：社内便データモデル＋build派生ビュー（mail.md・スレッド・受信箱）＋連携タブのカード/スレッドモーダル/返信。
- **P4**：複数部署ブレークダウンの /Chack 連携・運用文書化。
- 受け入れ：①全タブがカード/モーダル/フィルタ/自動更新で統一 ②jdgを画面で承認/差戻しでき判定記録に乗る ③社内便が単一書き手のまま往復・受信箱が派生表示・社長が画面から返信できる ④複数部署タスクが段階/並行で回る ⑤build警告なし・生成JS自己チェック通過・60秒更新がモーダル中は停止。
