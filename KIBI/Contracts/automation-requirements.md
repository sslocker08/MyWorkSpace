# KIBI 自動化パイプライン 要件定義書（automation-requirements）

版：req v0.1（2026-06-13 起案・社長室／EC・情報システム部 システム設計担当）。
位置づけ：三社フロー自動化の**要件定義**（実装の根拠）。設計提案＝`automation-design-draft.md`、契約上の枠組み＝`master-agreement.md`（特に第13・14・17・20条）、機密＝`security-policy.md`、様式＝`forms.md`。
**本書の採択（＝運用モデルの変更）は重大変更（契約第14条）につき、Sota承認＋tpr審査を要する。** 本書はその審査に付すための要件記述であり、実装の発注（Tier2＝外注可）はSota承認後に行う。

## 1. 目的とスコープ

### 1.1 目的
発注（ord）から統合（Internal反映）までの三社フローを、**全自動でありながら、進捗はスマホ通知、重要事項はその都度Sota承認**で進める基盤を定義する。自動化の狙いは「人間を不要にする」ことではなく、**人間が判断すべき所だけにSotaを集中させ、それ以外の待ち時間を自動で詰める**こと。

### 1.2 設計哲学（KIBI「急がない」との両立）
- 品質ゲート（内部監査・MAGI審査・人間承認）は**省略しない**。自動化は待ち時間の自動詰めに限る。スピードのために監査・審査・承認を飛ばさない（draft §7・契約第18条15項と整合）。
- 迷ったら止める（fail-closed）。判定不能・例外・閾値超過は自動進行せず人間へ。

### 1.3 スコープ
| 含む | 含まない |
|---|---|
| ord（発注）の状態追跡・自動再開・通知・承認回付 | Tier0/本番/決済/認証/顧客データの自動処理（恒久的に対象外） |
| Claude側 `/loop`・cron による受入査読/diff照合/統合（軽微・中規模） | `Internal/` 本体への自動コミット（統合は社長室セッションが実施） |
| Codex側 watcher による着手の自動起動（段階導入） | 外部委託先の自律的な再委託（契約別紙C-3で禁止） |
| MAGI審査の回付管理（依頼・受領の自動検知。審査自体は人間運用） | MAGI判定の自動生成・自動採用 |
| Slack進捗通知・ダッシュボード経由のスマホ承認 | 公開設定変更・新リモート追加（契約第20条13項＝Sota） |

### 1.4 現実の制約（正直な前提）
- リポジトリはローカルMac。**Claude Code（MAX×5）とCodex（GPT Plus）は別製品で共通イベントバスが無い** → ファイルフラグのポーリングで疎結合する（同一マシン＝ファイル共有が使える利点を活用）。
- 完全な無人実行には **`launchd` 等のローカル常駐**が要る（`/loop` は開いたClaude Codeセッションを要する／cloud routine はローカルrepoへ到達できない）。常駐の起動・停止はSotaの環境操作。
- 通知は既存 `SLACK_WEBHOOK_URL`（env・Slackモバイルpush）を第一候補とする。スマホ承認はローカル `serve.js` ダッシュボードを Tailscale / Cloudflare Tunnel で安全公開し、既存レビュータブの承認/差戻しボタンを使うのを MVP とする（新規コード最小）。

## 2. アクターと自動/手動の境界

| アクター | 実体 | 自動でできること | 必ず手動（人間/専用セッション） |
|---|---|---|---|
| **Sota（社長）** | 人間 | （なし。承認・裁定のみ） | 重要事項の承認・裁定・常駐の起動停止・環境/秘密設定 |
| **社長室 Claude**（`/loop`・cron） | Claude Code セッション | スキャン巡回・完了検知・受入査読・diff照合・**軽微/中規模の統合**・通知発火・承認回付 | 重大変更の確定・`GATE:human` 案件の前進・新規発注の起案 |
| **Codex Worker** | Codex（GPT Plus） | watcher 起動による着手・実装・自己点検提出（Tier2案件） | （Internal直読・範囲外編集は恒久禁止） |
| **Codex Internal Auditor** | Codex 別セッション | `.WORKER_DONE` 検知での内部監査自動起動 | （成果物の直接修正は禁止） |
| **KIBI-MAGI** | 3観点合議（GPT×2・Claude） | 審査依頼/結果の**回付検知**（自動）。`inbox/` 投入と判定保存は代行記録 | 審査判断そのもの（人間運用・別チャット起動） |
| **Ollama** | ローカルLLM | Tier1可の整形・要約・通知文生成・ダミーデータ処理 | （外部送信ゼロ。Tier0非接触） |

境界の原則（契約第5・7〜9・11条由来）：**統合できるのは社長室のみ**。External/ThirdParty は `Internal/` を自動でも手動でも触れない。MAGI判定は自動採用しない（人間運用）。

## 3. チケット種別 × 自動着手の対象/非対象

| 種別 | 意味 | 場所 | 自動着手 | 規則 |
|---|---|---|---|---|
| **ord-\<vendor\>-###** | 発注（実装） | `External/<Vendor>/Orders/` | **条件付き可** | `GATE:auto`（Tier2・軽微/中規模）のみ自動。判定＝§4 |
| **req-\<dept\>-###** | 部署間依頼 | `Internal/Secretary/status/` | 否（検知のみ） | Internal内の人間/部署運用。自動化は通知のみ |
| **jdg-\<dept\>-###** | 判断依頼（社長室起票） | `Internal/Secretary/status/` | 否 | 判断＝人間/社長室セッション。自動進行しない |
| **tpr-###** | 第三者審査 | `ThirdParty/Cases/` | **回付のみ自動** | 依頼投入・結果受領の検知は自動。**審査判断は人間運用・自動採用しない** |
| **fbk-hq-###** | 社長フィードバック | `HQ.md`（serve.js） | 記録のみ | 承認/差戻しの**記録レーン**として再利用（§6） |

自動着手の最小条件（ALL）：① STATE 行が機械可読で読める ② `GATE:auto` ③ Tier2以下 ④ `locks.md` に競合なし ⑤ サーキットブレーカ未発火（§7）。一つでも欠ければ着手せず通知（fail-closed）。

## 4. GATE 判定規則（変更区分 × Tier × 領域）

各 Order の `order.md` 冒頭に機械可読1行を持つ（draft §1）：
`<!-- STATE: 発注済|着手|提出済|監査済|審査中|受入|差戻し|統合済|完了|中止 LEVEL: 軽微|中規模|重大 GATE: auto|human TIER: 0|1|2|3 AREA: Internal|External|ThirdParty|Contracts -->`
STATE/GATE 行の**書き手は社長室のみ**（単一書き手維持・契約第12条）。GATE は発注時に社長室が確定し、自動段はこれを読むだけで書き換えない。

### 4.1 GATE:human（自動進行禁止＝必ず人間で停止）
契約第20条・第14条「重大」と一対一で対応させる。次のいずれかに該当したら GATE:human：
1. **重大変更**（LEVEL=重大）：部署構造・KIBI憲章・AI役割定義・受入基準の変更、会社運営方針への影響、MAGI設計変更、情報保護方針変更、思想/世界観を大きく変える変更（契約第14条）。
2. **決済 / 認証**：本番の決済・認証に関わる一切（同上）。
3. **本番デプロイ**：kibi-fragrance.jp 本番への反映（System 別紙B「本番デプロイ＝外注不可」）。
4. **外部AIへの大規模情報共有**：Tier1の例外共有・大量スナップショット投入（契約第20条7項）。
5. **契約 / 憲章 / 受入基準の変更**：`Contracts/**`・`Internal/Strategy/` 憲章・`acceptance-criteria.md` の改訂（契約第21条）。
6. **Tier0 接触**：`.secrets/`・`_Records/`・処方原本・顧客個人情報（恒久禁止。検知時は停止＋違反記録）。
7. **領域横断の `Internal/` 反映で重大**：統合先が中核部署（Strategy/Finance/Legal/Development 中核業務）の中核（契約第20条12項）。

GATE:human の Order は、**いかなる自動段でも人間承認なしに次STATEへ進めない**。自動段は検知して**スマホへ承認依頼を出し、Sota応答を待つ**（§5・§6）。

### 4.2 GATE:auto（自動進行可）
次を**すべて**満たすときのみ：
- LEVEL ∈ {軽微, 中規模}（重大は不可）。
- TIER ≤ 2（Tier2以下。Tier1は外部委託先へは出さない＝Ollama限定。Tier0は不可）。
- AREA が自動反映先として安全（統合先が `Internal/` の非中核、または External/ThirdParty 内のフロー前進）。
- 作業種別が軽微/中規模の定型（契約第14条の例）：コード整形・テスト・差分照合・ダミーデータ処理・Markdown整形・既存仕様に基づく機能追加・管理表/ダッシュボード拡張。
- §7 のサーキットブレーカが未発火。

GATE:auto でも**中規模は Codex内部監査必須**（契約第14条）、中規模以上で社長室が指定した場合は MAGI審査を回付する（自動着手はするが、審査・監査の関門は省略しない）。

### 4.3 判定の優先と既定
- 区分が曖昧・判定不能・複数該当 → **GATE:human に倒す（fail-closed）**。
- 既定値は `GATE:human`。社長室が明示的に `GATE:auto` を付与した Order のみ自動進行する。
- ロック競合・STATE行欠落・Tier未記載 → 自動進行せず通知のみ。

## 5. 通知要件（何を・いつ・どのchannelで・スマホへ）

第一channel＝**Slack（`SLACK_WEBHOOK_URL`・モバイルpush）**。Slack不通時はダッシュボードのパイプラインタブにも全件残す（通知欠落での停止を避けるが、承認待ちは進めない）。

| イベント | いつ | channel | スマホ | 本文（簡潔体・1〜2行） |
|---|---|---|---|---|
| 自動着手 | watcher/loop が着手した時 | Slack | push | `[auto] ord-### 着手（Tier2・中規模）` |
| 段階完了 | `.WORKER_DONE`/`.AUDITOR_DONE`/`.VERDICT_READY` 検知 | Slack | push | `[done] ord-### 監査済 → 社長室受入待ち` |
| **承認依頼** | GATE:human / 重大 / diff照合不一致 | Slack＋ダッシュボード | push（要対応） | `[承認待ち] ord-### 〈件名〉 → 承認/差戻しはダッシュボードで` ＋承認URL |
| 自動差戻し | diff不一致・範囲外編集検知 | Slack | push | `[差戻し] ord-### diff不一致につき自動差戻し` |
| サーキットブレーカ発火 | 連続失敗N・Secretヒット・上限超過 | Slack | push（警報） | `[停止] パイプライン停止：〈理由〉。再開はSota` |
| 統合完了 | 軽微/中規模を自動統合した時 | Slack | push | `[統合] ord-### を Internal へ反映・完了` |
| 日次サマリ | 1日1回（夕） | Slack | push | 待ち行列・発火・完了の集計（`_pipeline.json` 由来） |

通知は**何が起きたか＋次に誰の番か**を必ず含む（draft §2 の「誰の番か」表と同じ語彙）。通知本文には Tier1以上の中身を載せない（IDと状態のみ。機密はダッシュボードのローカル面でのみ表示）。

## 6. 承認要件（その都度承認・承認の記録）

### 6.1 承認の対象
§4.1 の GATE:human 全件＋自動差戻し後の再開＋サーキットブレーカ解除。これらは**その都度、個別に**Sota承認を要する（一括の事前承認で重大を素通しさせない）。

### 6.2 承認の経路（MVP→上位案）
- **MVP（新規コード最小・推奨）**：ローカル `serve.js`（`http://127.0.0.1:4310`）を **Tailscale または Cloudflare Tunnel** で安全公開 → スマホのブラウザから既存「レビュー」タブの**承認/差戻しボタン**で応答。承認は `HQ.md` の `fbk-hq-###` として記録される（serve.js 既存の `/review` 経路）。
  - 公開は限定（Tailnet 内 or Cloudflare Access 認証）。**公開設定はSotaが行う**（契約第20条13項に準じ、トンネル常設はSota判断）。
- **上位案（将来）**：Slack インタラクティブ（ボタン付きメッセージ）＋ Netlify 関数で受け、署名検証のうえ承認フラグをrepoへ書く。新規コードと外部公開面が増えるため、採用は別途 tpr 審査。

### 6.3 承認の記録（証跡・契約第17条）
- 承認/差戻しは **`fbk-hq-###`（HQ.md）** を一次記録とし、対象 Order の `decision/` に Sota承認記録として転記する（誰が・いつ・何を・経路）。
- GATE:human を通過させた事実は当該 Order と `_pipeline.json` の遷移ログ（§7-6）に必ず残す。**承認なき前進は契約違反**として記録対象。
- 重大変更は `Internal/Secretary/boards/decisions.md`（dec-###）にも決定として残す（契約第17条2項）。

## 7. 非機能要件（同時実行・レート・障害時fail-closed・証跡）

### 7.1 サーキットブレーカ（必須・draft §5 を要件化）
| # | 装置 | 規則 | 発火時の動作 |
|---|---|---|---|
| 1 | **重大ゲート** | `GATE:human`/`LEVEL:重大`/`TIER:0` は自動進行禁止 | 停止＋承認依頼通知 |
| 2 | **同時実行上限** | GPT同時セッション **≤3**。**MAGI審査中は Codex Worker を1に絞る** | 超過分は待機（watcher が起動を抑止） |
| 3 | **ロック** | `locks.md` 凍結中ファイルへの並行発注/着手を禁止 | 着手せず通知 |
| 4 | **diff照合** | 統合前に `changed-files.md` と実差分を機械突合 | **不一致は自動差戻し**＋違反記録 |
| 5 | **連続失敗で停止** | 連続 **N回**（既定3）失敗 → パイプライン停止 | 停止＋警報通知（再開はSota） |
| 6 | **Secret走査** | コミット/統合前に鍵パターン走査（`sk-`・`ghp_`・`AIza`・`pk_live`・`sk_live`・`BEGIN PRIVATE KEY`・`password=` 等／security-policy §6） | **ヒットで即停止**＋当該除外＋記録 |
| 7 | **範囲外編集** | 着手宣言（`declaration.md`）外のファイル変更を検知 | 自動差戻し＋違反記録 |
| 8 | **日次上限** | 1日あたりの自動着手/自動統合の件数上限 | 上限到達で当日打ち止め＋通知 |

### 7.2 レート・同時実行
- 同時GPTセッション ≤3（MAGI審査中は Codex Worker=1）。watcher は起動前に現行セッション数を確認し、超過なら起動を遅延。
- ポーリング間隔は過負荷を避ける既定（例：scan 30〜60秒、watcher は fswatch のイベント駆動）。Sota設定で調整可。

### 7.3 障害時 fail-closed
- 判定不能・例外・タイムアウト・通知失敗・状態不整合は**進めない方向に倒す**（停止して通知）。
- 自動統合は**ドライラン→diff照合→反映**の順。照合不一致は反映しない。
- 緊急例外（本番障害・セキュリティ事案のみ）は自動化を経由せず、契約第19条4項の事後24h起票に従う。

### 7.4 証跡（契約第17条）
- 全自動遷移を `_pipeline.json`（機械可読）と各 Order に追記（誰の番か・遷移時刻・GATE判定・ブレーカ発火）。事後監査可能にする。
- 文書証跡は削除・改変禁止。データ類（`inputs/` スナップショット・ダミーデータ）は役割終了後に削除し削除記録を残す（security-policy §5）。

### 7.5 機械可読ハンドオフ（draft §1・§2 を要件化）
- 各サブフォルダ完了時のセンチネル：`work/.WORKER_DONE`・`audit/.AUDITOR_DONE`・`Cases/<tpr>/.VERDICT_READY`・`decision/.INTEGRATED`。書き手は所有者のみ（契約別紙A）。
- スキャンの単一窓口 `node Internal/Secretary/tools/orders-scan.js`（新規・要実装）：`External/<Vendor>/Orders/*/` と `ThirdParty/Cases/*/` を走査→「誰の番か」一覧＋`_pipeline.json` 出力。`locks.md` と突合し競合検出。ダッシュボードの新タブ「パイプライン」になる。

## 8. 受入基準

| # | 基準 | 検証方法 |
|---|---|---|
| 1 | GATE:human 案件が**自動で次STATEへ進まない**（承認なしに前進ゼロ） | 重大ダミー Order で巡回→停止＋承認依頼通知のみを確認。`_pipeline.json` に前進記録が無いこと |
| 2 | GATE:auto（Tier2・中規模ダミー）が着手→監査→受入→統合まで自動で流れる | ord-001 系ダミーで一巡。各遷移が `_pipeline.json` に記録されること |
| 3 | diff照合不一致で**自動差戻し**＋違反記録が出る | `changed-files.md` と実差分を意図的にずらして発火を確認 |
| 4 | 同時GPTセッション ≤3、MAGI審査中は Worker=1 が守られる | watcher の起動抑止ログで確認 |
| 5 | Secret走査ヒットで即停止＋通知＋当該除外 | ダミーに `sk_live_...` を混入させ発火を確認（実鍵は使わない） |
| 6 | 進捗がSlackへpushされ、**スマホで承認/差戻し**ができる | Slack通知受信→トンネル経由でダッシュボード承認→`fbk-hq-###` 記録を確認 |
| 7 | 承認の記録が `fbk-hq-###`＋当該 `decision/`＋重大は decisions.md に残る | 承認1件を流して三箇所の整合を確認 |
| 8 | 連続失敗Nで停止し、再開にSota操作を要する | 失敗を連続注入→停止＋警報→Sota無しでは再開しないことを確認 |
| 9 | Tier0/本番/決済/認証/Internal直読が自動経路に**一切混入しない** | 経路の対象範囲レビュー＋防火壁（PROTECTED 正規表現）テスト |
| 10 | 自動化により監査・審査・人間承認の関門が省略されていない | 中規模ダミーで Codex内部監査が必須通過していること、重大で MAGI＋Sota を経ること |
| 11 | 全自動遷移が事後監査可能（証跡完備・契約第17条） | `_pipeline.json` と Order 記録の突合 |
| 12 | 本書が契約第14/20条と矛盾しない | GATE:human の7項目 ↔ 第20条/第14条「重大」の対応表レビュー |

共通基準：fail-closed が既定であること／範囲外編集ゼロ／外部依存の無断追加なし／簡潔体。

## 10. 契約との整合（要点）
- 第13条フロー（発注→着手→提出→監査→審査→受入→統合→完了）を**自動段が代替するのは「待ち時間の検知と前進」だけ**。判断・統合・承認の主体は変えない。
- 第14条：重大＝GATE:human、中規模＝Codex内部監査必須＋必要に応じ MAGI、軽微＝自動可。
- 第17条：全遷移を証跡化。第18条：禁止事項（範囲外編集・内部監査のみの重大承認・Internal直読等）を自動段でも遵守。

- 第21条：本書の採択・改訂は重大改訂手続き（MAGI審査＋Sota承認）。発効後 `changelog.md` に記録する。
