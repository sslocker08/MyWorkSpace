# 採番規則とチケット・ライフサイクル規約（numbering & tickets）

複数案件（インスタンス）で共通の、ID採番・チケット/オーダーの状態遷移・発行管理権限・GATEレベル・「誰の番か」の機械可読表現を定める汎用規約。固有値（vendor名・部署scope一覧・MAGI構成）は `instance.config` と各インスタンスの `Contracts/` で具体化する。優先順位は上位契約（master-agreement・security-policy）に従う。

## 1. 採番規則（ID prefix）

IDは小文字・連番3桁ゼロ詰め（###）を基本とする。`<vendor>`・`<scope>` はインスタンスの `instance.config` 定義に従う（vendor＝外注先キー／scope＝部署または領域キー）。

| 種別 | 形式 | 例 | 採番単位 | 記録の置き場所 |
|---|---|---|---|---|
| 外注オーダー | `ord-<vendor>-###` | `ord-codex-001` / `ord-ollama-001` | vendorごとに連番 | `External/<Vendor>/Order(s)/ord-<vendor>-###/` |
| 第三者審査 | `tpr-###` | `tpr-001` | インスタンス全体で連番 | `ThirdParty/Cases/tpr-###/` |
| タスク | `tsk-<scope>-###` | `tsk-hq-009` / `tsk-mkt-004` | scopeごとに連番 | 当該scopeのボード（`Secretary/boards/tasks.md` 等） |
| 決定 | `dec-###` | `dec-014` | インスタンス全体で連番 | 決定ログ（`Secretary/boards/judgments.md` 等）・`Contracts/changelog.md` |
| フィードバック | `fbk-###`（HQ宛は `fbk-hq-###` 可） | `fbk-039` / `fbk-hq-026` | 発行元scopeで連番（HQ宛は別系列） | `Secretary/boards/feedback.md` |
| 判断 | `jdg-<scope>-###` | `jdg-brd-001` / `jdg-sls-001` | scopeごとに連番 | `Secretary/boards/judgments.md` |

- IDは発行後に再利用・欠番詰めをしない（追跡性のため）。中止・取消も番号は保持し STATE で表す。
- `<vendor>` 追加時は外注台帳（`External/_vendors.md`）に登録してから採番する。`<scope>` は `instance.config` の部署/領域キーと一致させる。

## 2. ライフサイクル状態（STATE）

オーダーとチケットの状態は次の系列を正本とする（上位＝automation設計の `STATE` 遷移に一致）。

`準備中 → 発注 or 起票 → 作業中 → レビュー → 承認待ち → 受入/完了`（保留＝rate-limited は枠回復まで横に退避し、失敗扱いしない）

| STATE | 意味 | 主な担い手 | 次の合図 |
|---|---|---|---|
| 準備中 | 起票前の下書き（発注書・要件の整備中） | 起票元 | 発注/起票で前進 |
| 発注済／起票済 | 発注・起票が確定し着手待ち | 担当（Worker/担当部署） | 着手 |
| 作業中（着手） | 実作業中 | 担当 | 提出（成果物＋自己点検） |
| レビュー | 内部監査・diff照合・（必要なら）第三者審査 | Auditor／社長室／ThirdParty | 監査済・審査済 |
| 承認待ち | GATE判定が `中`/`重` で人間判断待ち | Sota（重）／社長室（中） | 承認/差戻し |
| 受入／完了 | 受入判定→統合→クローズ | 社長室 | クローズ |
| 保留（rate-limited） | 外部枠超過などで一時退避（**失敗ではない**） | システム | 枠回復で元STATEへ自動復帰。整形系は無枠先（Ollama等）へ退避可 |
| 中止 | 取りやめ（番号は保持） | 起票元／社長室 | クローズ |

- オーダーの詳細STATE系列は様式に従う：`発注済 → 着手 → 提出済 → 監査済 →(審査中)→ 受入|条件付受入|差戻し → 統合済 → 完了|中止`。本節の6段は横断要約であり、オーダーはこの詳細系列へ写像する。
- 物理的な完了の合図は各サブフォルダの**センチネルファイル**（`work/.WORKER_DONE`・`audit/.AUDITOR_DONE`・`decision/.INTEGRATED`、審査側 `Cases/<tpr>/.VERDICT_READY`）で表す。STATE行とセンチネルが食い違う場合はセンチネル（より新しい合図）を優先する。
- 保留は時間切れ・rate-limit由来の退避であり、連続失敗ブレーカ（停止扱い）とは区別する。

## 3. 発行・管理権限

| 行為 | 権限保有者 |
|---|---|
| 発注（`ord-<vendor>-###` の起票・発注書記入） | **社長室の専管**（External・ThirdPartyは起票しない） |
| 第三者審査の起票（`tpr-###`）・スナップショット供給 | 社長室専管 |
| 監視・追跡・タスク管理（`tsk-<scope>-###` の起票/更新・ボード/ダッシュボード維持） | 秘書室（管制塔） |
| 軽微（**Tier2 かつ `GATE: auto`**）の推進 | 秘書室の自室判断で可 |
| 決定（`dec-###`）・契約改訂・新規vendor採用・支出 | Sota承認必須（社長室が記録） |

- 外部（External）・ThirdParty からの進言は、社長室経由でSotaへエスカレーションする（直接の発注・起票はしない）。
- 書き手は単一に保つ（STATE行・発注書は社長室、着手宣言・自己点検はWorker、監査レポートはAuditor、審査はMAGI）。

## 4. GATEレベル

GATEは「自動で次へ進めてよいか」を表す。`LEVEL: 重大` または Tier1超の情報共有が絡む遷移は、ラベルに関わらず必ず最上位（`重`＝人間承認）へ落とす。

| GATE | 意味 | 進め方 | 該当例 |
|---|---|---|---|
| `auto` | 軽微・自動進行可 | Watcher/秘書室が自動前進（Tier2かつ正本へ触れない範囲に限る） | コード整形・テスト・diff照合・ダミーデータ整形・md整形 |
| `中` | 社長確認 | 社長室が確認して前進（中規模変更・通常の受入判定） | 中規模オーダーの受入・統合 |
| `重` | Sota承認 | 人間（Sota）承認なしに次へ進めない（サーキットブレーカ） | 契約・憲章・本番デプロイ・決済/認証・新規vendor採用・支出・外部AIへの大規模共有・`LEVEL: 重大` |

- `auto` の前提：成果物がTier2スナップショット内で完結し、Internal正本へ触れないこと。これを外れる場合は `中` 以上へ昇格する。
- `重` の停止点は、いかなるセンチネルが揃っても人間承認なしに自動遷移しない（automation設計のサーキットブレーカに一致）。
- API課金ゼロが絶対条件のため、自動進行は常にローカル計算（相互API呼び出しはしない）。

## 5. 「誰の番か」のフロントマター規約（機械可読）

オーダー/チケットのステータス行末尾に、人にも機械にも読める1行のHTMLコメントを必ず添える。走査ツール（`orders-scan.js` 等）がこれを読み「次に誰の番か」を判定する。

```
<!-- STATE: <状態> LEVEL: 軽微|中規模|重大 GATE: auto|中|重 OWNER: <次の担い手> UPDATED: <YYYY-MM-DDThh:mm+09:00> -->
```

- **STATE**（現在地・単一書き手＝発行管理者）：第2節の系列値（保留は `保留(rate-limited)`）。
- **LEVEL**（変更区分）：`軽微｜中規模｜重大`。発注書本文の「変更区分」と一致させる。
- **GATE**（自動進行の可否）：`auto｜中｜重`。`LEVEL: 重大` または Tier1超共有が絡む場合は機械的に `重` へ落ちる。
- **OWNER**（次の担い手）：例 `Worker｜Auditor｜社長室｜秘書室｜MAGI｜Sota`。
- **UPDATED**：最終更新時刻（JST・ISO8601）。

走査の優先順位：センチネルファイルが存在する場合はセンチネル（より新しい合図）を優先し、STATE行と食い違えばセンチネル側で次工程を示す。`GATE: 重` 案件は揃っても自動前進させず、承認待ちとして強調表示（スマホ通知）する。
